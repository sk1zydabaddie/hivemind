# Full-codebase audit — 2026-08-17

This register covers the Core TypeScript package, the React desktop client, the
Tauri shell, packaging/install flow, and the installed build `26.817.1726`.
Findings are counted by independently testable failure, not by affected line or
field. A shared cause with several visible consequences is named explicitly.

## Invariants used

- React is a thin client. It owns no authoritative state and cannot enforce a
  safety gate.
- Control flow never depends on user-facing message text.
- Authoritative project state is durable state under `.hivemind/`.
- Guarantee-enforcing code is deterministic and fails closed.
- A desktop fix is not verified until the installed app exhibits it.

## Immediate priority

### A-01 — Critical — updater capability bypasses the audited install gate — fixed

`desktop/src-tauri/capabilities/default.json` grants `updater:default`. Tauri's
generated updater ACL defines that set to include check, download, install, and
download-and-install. Any webview code can therefore invoke the plugin install
path directly and bypass `take_newer_version`, whose Rust-side idleness check is
supposed to be the only install authority. `desktop/test/updater.test.ts`
currently asserts the unsafe permission, and `main.rs` incorrectly documents
the JS API as unreachable.

Fixed in the phase following this audit: the WebView now has explicit denials
for check, download, install, and download-and-install. It receives no updater
grant at all. The plugin remains registered for Rust's internal
`UpdaterExt`; `newer_version` and `take_newer_version` remain the only product
routes, and the regression test rejects both the aggregate permission and any
future direct frontend import.

### A-02 — High — production updater endpoint is unreachable

The installed app consistently reports that it cannot check for updates. Its
configured endpoint,
`https://github.com/sk1zydabaddie/hivemind/releases/latest/download/latest.json`,
returns HTTP 404, so an unauthenticated installed client cannot discover a
release. Local updater tests do not exercise the production endpoint.

Done: publish a reachable signed manifest or move the endpoint to a reachable
release channel, then add a release-time remote manifest probe.

### A-03 — High — setup succeeds with no verification command

`src/init.ts` can write an empty `test_command`; `src/config.ts` accepts any
string, including empty; the desktop then considers setup complete and enables
Work. Integration later rejects the same project because
`config.test_command` is empty. The installed Skybound project reproduced this:
the package has no test script, Settings shows a blank check, and Work is
enabled.

Done: setup must remain incomplete with a plain-language action until an honest
verification command exists, or the user explicitly chooses a supported
no-check policy that downstream gates also understand.

### A-04 — High — provider setup spend is missing from the live meter

The installed Skybound setup recorded three Codex reservations totalling
122,977 tokens in `.hivemind/resource/`, while the Work footer displayed
`0 calls` and `0 + 0 held`. This materially understates paid usage.

Done: derive the meter from the same durable ledger that records setup probes,
with an installed-app regression fixture.

### A-05 — High — provider setup activity is missing from project history

The same three durable provider probes produced no event history: the Project
surface said `Nothing recorded yet`, and `events.jsonl` remained empty. Paid
project activity is therefore absent from the audit trail as well as the meter.

Done: record setup probes as durable project events, including provider,
purpose, result, and usage without exposing secrets.

### A-06 — High — required Hivemind project facts are left untracked

One-click Git setup makes the first commit before Hivemind initialization.
Initialization then creates `.hivemind/config.json` and
`.hivemind/.gitignore`, leaving both untracked with no visible prompt. A clone
of the committed project therefore does not contain the shared Hivemind
configuration.

Done: make project facts part of the explicit setup transaction or show a
blocking, one-click review/commit step after initialization.

### A-07 — High — one-click Git setup is not transactional

`initialize_git` writes `.gitignore`, creates `.git`, stages files, and commits
as separate mutations. Any failure after the first step leaves partial state.
The UI's error copy says nothing changed, which is false after such a failure.

Done: preserve and restore the pre-action `.gitignore` and remove only the
newly created repository on failure, or report the exact durable partial state
and give a safe recovery action.

### A-08 — High — settings can display and mutate stale project data

`SettingsDialog` retains its previous `view` when reopened and refreshes only
after render. Switching from Hivemind to Skybound visibly showed Hivemind's
worker state for the new project before the request completed, with controls
enabled. The effect is keyed to `open`, not the selected project, and does not
clear or lock stale values.

Done: key settings state by canonical project identity, clear it synchronously
on project change, and disable mutations until the matching inspection lands.

### A-09 — High — daemon messages are cast without runtime validation

`parseMessage<T>` performs `JSON.parse` followed by an unchecked TypeScript
cast. Syntactically valid older, malformed, or incompatible SSE payloads flow
into projection code as trusted messages and can throw outside the parser.

Done: validate event and output discriminants plus required fields at the
boundary; reject an invalid record visibly without killing later events.

### A-10 — High — task output can freeze silently

The project event stream has an `onerror` state, but the selected task output
stream has no `onerror`, reconnect status, or user-facing failure. A broken
output connection leaves a static transcript that looks current.

Done: expose interrupted/reconnecting state for the output stream and prove a
later event either reconnects or offers a retry.

## Installed-app and interaction findings

### A-11 — Medium — Agents empty state renders the Work composer

With no agents running, selecting Agents shows the same task composer used by
Work instead of an Agents-specific empty state or graph explanation. This was
reproduced in installed build `26.817.1726`.

### A-12 — Medium — full project record opens a blank dialog

On a fresh project, `See the full record` opens an empty modal. The underlying
list has no empty state even though the parent surface correctly says
`Nothing recorded yet`.

### A-13 — Medium — internal theme playground ships in production

Settings includes a panel labelled `EXPERIMENTAL temporary panel` and says it
will be deleted after design choices are made. It writes real style tokens and
local storage from the installed production app.

### A-14 — Medium — production UI reports its own known overflow

The shipped playground's `FIT CHECK` reports that the `Commands` dialog title
is 89 pixels wider than its box. The overflow is known to the application but
does not gate packaging.

### A-15 — Medium — autonomy mutation failure is not shown locally

The autonomy option invokes `onAction` with `void` and no local rejection
handler. Other Settings changes populate `error`; this path can fail without
feedback in the open dialog.

### A-16 — Medium — account inspection failure is rendered as no accounts

`AccountsPanel` deliberately hides itself when its load fails. Daemon or schema
failure is indistinguishable from a project with no configured accounts.

### A-17 — Medium — usage inspection failure is rendered as no usage

`ProjectTab` suppresses a rejected `config.inspect` and removes the usage
surface. The result resembles a valid empty project instead of a failed read.

### A-18 — Medium — provenance inspection failure removes the qualifier

`ProvenanceNote` suppresses `checks.inspect` failures. A missing daemon command
or incompatible response silently removes evidence context from the project
surface.

### A-19 — Medium — recent-project load failures empty the command palette

The app maps any `recent_projects` failure to an empty list. Users see no
projects and no error, repeating the same missing-command/empty-state failure
class as accounts and usage.

### A-20 — Medium — remembering a project fails silently

`remember_project` rejects into `undefined`. A project can appear to open
normally but never become reachable from recents, with no recovery path.

### A-21 — Medium — build-mismatch recovery captures a stale callback

The memoized project session calls `recoverFromBuildMismatch`, but the callback
is absent from the memo dependency list and changes with `projectPath`. A
mismatch after switching projects can inspect or restart using the previous
project path when no current connection is available.

### A-22 — Medium — durable collection compatibility remains unsafe

Shared daemon response records still declare 31 collection fields as required.
Making them optional produces 48 unguarded client reads. Older durable records
can therefore crash or misrender instead of treating absent collections as
empty. This is the measured open item already recorded in `docs/STATE.md`.

### A-23 — Medium — five implemented action types have no desktop control

Core accepts `manual_task.review`, `manual_task.authorize`,
`verify.characterize`, `quality.best_of_n`, and `quality.draft_refine`; the
desktop action union knows their names, but no production control invokes
them. Implemented product capabilities are unreachable.

## Security and dependency findings

These are distinct vulnerable dependency packages, but share one missing
guard: neither root nor desktop shipping runs a production advisory audit.
Exploitability must be reviewed before choosing upgrade or containment.

### A-24 — High — `fast-uri` host confusion advisories in the MCP path

Root production dependencies resolve vulnerable `fast-uri@3.1.2` through
`@modelcontextprotocol/sdk`. The SDK is used by the production MCP HTTP
transport, so this is not an unused package-lock entry.

### A-25 — High — `ip-address` trust-boundary advisories in the MCP path

Root production dependencies resolve vulnerable `ip-address@10.2.0`, including
SSRF/trust-boundary parsing advisories, through the production MCP SDK.

### A-26 — Medium — `hono` advisories in the MCP path

Root production dependencies resolve vulnerable `hono@4.12.25` through the
production MCP SDK.

### A-27 — Medium — `@hono/node-server` Windows path traversal advisory

Root production dependencies resolve vulnerable
`@hono/node-server@1.19.14`. The advisory concerns encoded backslashes on
Windows, the primary installed platform.

### A-28 — Low — vulnerable `nanoid` in the desktop build toolchain

The desktop dependency graph resolves `nanoid@3.3.16` through PostCSS/Vite with
a high-severity advisory. It is a build-time rather than installed-runtime
path, but untrusted build input can still affect packaging infrastructure.

### A-29 — Medium — shipping has no dependency advisory gate

Neither package exposes a security-check script and `npm run ship` does not run
an advisory audit. Known production dependency vulnerabilities can remain green
through every documented release check.

## Static-analysis, migration, and maintainability findings

These are not counted as 170 or 48 separate bugs. Each item is one missing
guard or one cleanup class with a measured blast radius.

### A-30 — Medium — Core permits 170 unchecked indexed reads

Enabling `noUncheckedIndexedAccess` exposes 170 production errors across 26
files, concentrated in manager, workspace actions, learned routing, value
quality, adapter, and routing. Some are logically guarded; the missing compiler
rule nevertheless allows an unguarded read to enter safety-critical code
without review.

### A-31 — Low — production contains 16 compiler-proven dead symbols

Enabling unused-local/parameter checks identifies 16 unused imports, helpers,
or parameters across Core plus four in the desktop. They add misleading paths
in areas including events, daemon, checkpoint, project sharing, and UI state.

### A-32 — Low — 18 production exports have no production consumer

`npm run audit:unreached` reports 18 exported production functions unreachable
from production imports, including rollback, directory probe, adapter, endpoint
surface, and non-goal helpers. Some have tests, but test-only reachability does
not make a product path live.

### A-33 — Medium — 21 durable formats remain v1-only without migration

The schema audit recorded in `docs/STATE.md` finds 21 modules that reject any
schema version other than 1 and provide no migration. Durable project state is
longer-lived than a build, so upgrades can strand otherwise valid projects.

### A-34 — Low — Rust tests leak child processes on failure paths

Clippy identifies two spawned test children that are never waited on. They can
become zombies on supported Unix targets and make repeated test runs less
reliable.

### A-35 — Low — Rust connection helper has an overgrown argument boundary

Clippy rejects `connect_project_with` for eight arguments. The function mixes
path resolution, daemon discovery, CLI location, build identity, and command
execution dependencies, making gate behavior harder to test in isolation.

### A-36 — Medium — required static checks are absent from normal verification

The regular suites are green while Clippy with warnings-as-errors, unused-code
checks, unchecked-index checks, and dependency audits all fail. None is wired
into root or desktop verification, so regression protection excludes the
classes this audit found.

## Shared causes

The 36 findings do **not** share one cause. They cluster into four causes:

1. **Boundary mismatch:** A-01, A-02, A-09, A-10, A-21, A-22, A-33.
2. **Setup is declared complete too early:** A-03 through A-07.
3. **Failure is rendered as absence:** A-15 through A-20.
4. **Checks are narrower than the shipped product:** A-11 through A-14 and
   A-23 through A-36.

The highest-risk first repair is A-01 because it invalidates an explicit safety
claim. The first user-journey repair should then be A-03 through A-07 as one
bounded setup-integrity phase; those defects explain why a newly selected
folder immediately falls into contradictory states.
