- Control flow never depends on user-facing message text.
- Authoritative project state is durable state under `.hivemind/`.
- Guarantee-enforcing code is deterministic and fails closed.
- A desktop fix is not verified until the installed app exhibits it.

## Immediate priority

### A-01 — Critical — updater capability bypasses the audited install gate — fixed

`desktop/src-tauri/capabilities/default.json` grants `updater:default`. Tauri's
generated updater ACL defines that set to include check, download, install, and
download-and-install. Any webview code can therefore invoke the plugin install
path directly and bypass `take_newer_version`, whose Rust-side idleness check is
supposed to be the only install authority. `desktop/test/updater.test.ts`
currently asserts the unsafe permission, and `main.rs` incorrectly documents
the JS API as unreachable.

Fixed in the phase following this audit: the WebView now has explicit denials
for check, download, install, and download-and-install. It receives no updater
grant at all. The plugin remains registered for Rust's internal
`UpdaterExt`; `newer_version` and `take_newer_version` remain the only product
routes, and the regression test rejects both the aggregate permission and any
future direct frontend import.

### A-02 — High — production updater endpoint is unreachable — fixed

The installed app consistently reports that it cannot check for updates. Its
configured endpoint,
`https://github.com/sk1zydabaddie/hivemind/releases/latest/download/latest.json`,
returns HTTP 404, so an unauthenticated installed client cannot discover a
release. Local updater tests do not exercise the production endpoint.

Fixed on 2026-08-18. The repository is public, release `v26.818.803` publishes
the signed Windows installer and `latest.json`, and the configured endpoint is
reachable without GitHub authentication. `release:github` keeps a release in
draft until both assets exist and then runs an anonymous remote probe that
requires the exact stamped version, a credible signature, an HTTPS installer
URL, and an installer larger than one megabyte. The installed build
`26.818.803` opened with no unreachable-endpoint warning.

### A-03 — High — setup succeeds with no verification command

`src/init.ts` can write an empty `test_command`; `src/config.ts` accepts any
string, including empty; the desktop then considers setup complete and enables
Work. Integration later rejects the same project because
`config.test_command` is empty. The installed Skybound project reproduced this:
the package has no test script, Settings shows a blank check, and Work is
enabled.

Done: setup must remain incomplete with a plain-language action until an honest
verification command exists, or the user explicitly chooses a supported
no-check policy that downstream gates also understand.

### A-04 — High — provider setup spend is missing from the live meter — fixed

The installed Skybound setup recorded three Codex reservations totalling
122,977 tokens in `.hivemind/resource/`, while the Work footer displayed
`0 calls` and `0 + 0 held`. This materially understates paid usage.

Done: derive the meter from the same durable ledger that records setup probes,
with an installed-app regression fixture.

Fixed 2026-08-21. The invariant: every token the durable ledger records is
either on the run figures or on the setup figures — never absorbed, and never
inflating the ceiling-bound run numbers, because setup is not the run the
ceilings bind. Probes book under a session id minted by `probeUsageSessionId`
in `adapter-probe.ts`, and `workspace-inspection.ts` reads the same helper, so
the writer and the reader cannot drift. The regression injects probe entries
into the real captured walk-4 ledger and pins both directions; it was proven
to bite by disabling the reader branch (expected 3 calls, got 1). The idle
Work composer — where a person lands right after paying for setup — now shows
the meter whenever there is a figure to report; it hid the whole row before,
which is how the number stayed invisible even after the ledger fix. Verified
in installed build `26.821.1251` against Skybound itself: the meter reads
`0 calls … · setup 4 calls 134.8K`
(`docs/evidence/findings-installed-26.821.1251/a04-setup-spend-on-meter.png`).

### A-05 — High — provider setup activity is missing from project history

### A-06 — High — required Hivemind project facts are left untracked

One-click Git setup makes the first commit before Hivemind initialization.
Initialization then creates `.hivemind/config.json` and
`.hivemind/.gitignore`, leaving both untracked with no visible prompt. A clone
of the committed project therefore does not contain the shared Hivemind
configuration.

Done: make project facts part of the explicit setup transaction or show a
blocking, one-click review/commit step after initialization.

### A-07 — High — one-click Git setup is not transactional — fixed

`initialize_git` writes `.gitignore`, creates `.git`, stages files, and commits
as separate mutations. Any failure after the first step leaves partial state.
The UI's error copy says nothing changed, which is false after such a failure.

Done: preserve and restore the pre-action `.gitignore` and remove only the
newly created repository on failure, or report the exact durable partial state
and give a safe recovery action.

Fixed 2026-08-21, both halves of the Done line. The invariant: the action
either completes fully or leaves the folder byte-identical to how it found it
— and "Nothing changed." is now a MEASURED claim, not copy. The pre-action
`.gitignore` (or its absence) is captured before the first mutation; on any
failure the rollback removes only a `.git` this call created and restores the
file byte-for-byte. The shell returns a typed `GitSetupFailure` —
`nothing_changed` or `partial_state` with the leftovers named — and the screen
branches on the code, never the message; an unrecognizable error decodes as
`partial_state`, because unprovable cleanliness is claimed by nobody. Rust
regressions inject a failing runner into the real sequence and were proven to
bite (removing the rollback fails both on the exact assertions). Verified in
installed build `26.821.1251` by forcing real `git add -A` to fail with an
exclusive file lock: the screen read `Nothing changed. git add -A failed …`,
and the folder on disk had no `.git` and the original `.gitignore` bytes
(`docs/evidence/findings-installed-26.821.1251/a07-honest-failure.png`).

### A-08 — High — settings can display and mutate stale project data — fixed

`SettingsDialog` retains its previous `view` when reopened and refreshes only
after render. Switching from Hivemind to Skybound visibly showed Hivemind's
worker state for the new project before the request completed, with controls
enabled. The effect is keyed to `open`, not the selected project, and does not
clear or lock stale values.

Done: key settings state by canonical project identity, clear it synchronously
on project change, and disable mutations until the matching inspection lands.

Fixed 2026-08-21, by derivation rather than by clearing. Every stored answer
names the project it was fetched for, and the values the dialog renders are
derived — an answer for any other project, stale on screen or arriving late,
is structurally invisible, and there is no clearing step to forget. Mutations
stay disabled until this project's own `config.inspect` lands. The load effect
is keyed to `[open, projectPath]`. The first fix attempt cleared state with a
render-time adjustment instead; the installed walk caught it throwing React
error #185 during the switch, which is why the shipped shape writes no state
during render at all. The shape regression in `thin-client.test.ts` was proven
to bite by removing the derived read. Verified in installed build
`26.821.1251`: settings on Skybound showed its roles; after switching to an
untracked folder, the reopened dialog carried only the new project's path with
every control disabled and `Reading this project's settings…` placeholders
(`docs/evidence/findings-installed-26.821.1251/a08-settings-after-switch.png`).

### A-09 — High — daemon messages are cast without runtime validation

`parseMessage<T>` performs `JSON.parse` followed by an unchecked TypeScript
cast. Syntactically valid older, malformed, or incompatible SSE payloads flow
into projection code as trusted messages and can throw outside the parser.

Done: validate event and output discriminants plus required fields at the
boundary; reject an invalid record visibly without killing later events.

### A-10 — High — task output can freeze silently

The project event stream has an `onerror` state, but the selected task output
stream has no `onerror`, reconnect status, or user-facing failure. A broken
output connection leaves a static transcript that looks current.

Done: expose interrupted/reconnecting state for the output stream and prove a
later event either reconnects or offers a retry.

### A-37 — High — a completed read-only task leaves a worktree that closes the idleness proof forever

**Found:** 2026-08-21, by the installed walk verifying A-04/A-07/A-08 — it
opened the completed acceptance project and could not get past "Hivemind was
updated".

The 2026-08-21 acceptance run (`d7766e7`) shipped two write tasks and one
read-only review through the installed app. The review task, T-003, completed
with zero changes and was correctly counted into adoption coverage — that half
was fixed in `d7766e7` — but its task worktree was never removed:
`.hivemind/worktrees/T-003` still exists in
`D:\Projects\Hivemind Installed E2E Final 26.821.453`. `daemon_work` counts
task worktrees, so the project reports one task workspace forever, and every
gate resting on the idleness proof stays closed: the daemon restart refuses,
the auto-recovery after an update refuses, and the build bar offers nothing —
permanently, on a project whose run completed successfully.

This is F-4's shape arriving through a different leftover: there the artifact
nothing settled was a reservation, here it is a worktree, and in both cases
the remedies are gated on the thing the leftover broke. Evidence:
`docs/evidence/findings-installed-26.821.1222/open-project-timeout.png` and
its README.

Done when: completing a read-only task removes its worktree exactly as an
adopted write task's is removed; and the idleness inspection distinguishes a
worktree with no owner from work in flight, so an orphaned worktree degrades
to a cleanable state instead of a permanent refusal.

**Fixed 2026-08-22, as a class rather than a third instance.** The proof was
defeated twice by two different orphans because it counted artefacts; the
inputs it consults were enumerated and each got an ownership answer:

| Input | Orphan shape | What now proves it dead |
| --- | --- | --- |
| active reservations | daemon died mid-call (F-4) | daemon liveness (unchanged) |
| task worktrees | task finished, or crashed, under a live daemon (A-37) | the task's durable run state: a trail-closed task owns nothing |
| — workers | spawned detached; can outlive a dead daemon | `task.worker_process_started`/`_stopped` pids from the trail, judged by PL-1 |

The invariant: **an artefact is work only while something that can still
finish it is alive.** All judged off durable records, never by asking the
daemon — the daemon this proof most often judges is one an update left
behind, and a route added today is absent from every daemon old enough to
matter (a first design that asked over HTTP was withdrawn for exactly the
reason recorded in `identity.test.ts`). Fail-closed in every uncertain
direction: an unaccounted worktree is a run that is ahead, EPERM and ambiguity
mean alive, an unreadable trail is Unknown. The recovery: leftovers are named
and disregarded ("will be cleaned up when the background process next
starts"), and both adoption completion and daemon startup run a plan-grounded
reconciliation that removes exactly the finished-clean read-only class —
never a write task's worktree, whose branch adoption still needs.

Proven to bite in both directions by four mutations: reverting the leftover
classification, blinding the worker scan, dropping the reconciliation's mode
check (caught only after the fixture gained a zero-change write task — the
changed-files guard had masked it), and the trail-name seam guard (whose own
first draft could not bite and was widened). Verified installed: the
naturally bricked acceptance project opened straight to its work surface on
build `26.822.1349`, its leftover `T-003` worktree removed by the fresh
daemon's startup reconciliation
(`docs/evidence/findings-installed-26.822.1349/a37-bricked-project-heals.png`).

### A-38 — High — burst re-renders around project switching feed React nested-update storms

**Found:** 2026-08-22, by the installed walk's severe-log gate, three times in
three shapes. Opening or switching projects replays durable history as fast
as loopback delivers it; anything stateful that reacts per-render during that
burst can chain past React's nested-update limit (#185), and whatever handler
happens to flush — a Radix animation end, an onChange — is where the crash
surfaces.

Two instances are fixed: a render-time state clear in the settings dialog
(replaced by derived project-named reads, A-08), and Radix presence exit
animations storming during switches — where the fix also exposed that the
reduced-motion `.animate-in`/`.animate-out` rules had never matched the Radix
surfaces at all, because their animation arrives as Tailwind variant classes;
both suppressions now use substring selectors, and the replay/switch window
is anchored to lifecycle moments after the walk measured a message-trailing
window expiring two milliseconds before the project dialog's exit began.

One instance remains open: an intermittent chain surfacing through an
`onChange` handler during the switch-adjacent burst, stack recorded by the
walk's error listener (evidence in
`docs/evidence/findings-installed-26.822.1349/`). The walk's severe-log gate
is the guard holding this class; it must not be weakened to make a run green.

### A-39 — Medium — shell daemon liveness is pid-only, and a reused pid bricks attach

**Found:** 2026-08-22, live: Skybound's recorded daemon died, Windows handed
pid 23156 to a web browser, and the shell read alive-pid-plus-dead-HTTP as an
unhealthy live daemon — which `connect_project_with` correctly refuses to
write past, indefinitely, until the record was cleared by hand. The dead-end
shape again: every gate behaving correctly around one wrong premise.

The disproof is already on disk and unconsulted: `daemon.json` records
`started_at`, and a process whose start time is later than the record's
cannot be the recorded daemon. Core has recorded `process_instance_id` for
exactly this since F-4; the shell's `process_liveness` checks only that some
process answers to the number.

Done when: the shell's liveness verifies identity, not just existence — a pid
