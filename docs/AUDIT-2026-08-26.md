## Confirmed findings

### F1-01 — Eight audited actions have no product surface

**Severity:** High
**Class:** Capability built but unreachable
**Remediation:** Closed 2026-08-28 in Phase 9. Accounts and Project now invoke
the six retained actions from intended controls; the productless
`manual_task.review` / `manual_task.authorize` exception, dispatcher branches,
audit rows, fixtures, and tests were deleted. The exact consumer audit reports
zero gaps.

`accounts.add`, `manual_task.authorize`, `manual_task.review`, `memory.review_handoff`, `quality.best_of_n`, `quality.cancel`, `quality.draft_refine`, and `verify.characterize` are registered and audited Core actions, but neither the desktop client nor a Core-published queued action invokes them. The mechanism exists; the product cannot reach it.

### F1-02 — The non-goal quality gate is test-only

**Severity:** High
**Class:** Guarantee built but not enforced
**Remediation:** Closed 2026-08-28 in Phase 9. The active spec adoption path
rejects vacuous non-goals before any spec mutation or ratification, including
`None` / `N/A` forms, with a direct no-mutation regression.

`assessNonGoals` detects vacuous entries such as `"None"`, but no production path calls it. A direct probe showed the drafted-answer parser accepts a valid-looking specification containing `non_goals: ["None"]` while `assessNonGoals(["None"])` correctly rejects the same content. The check is real and tested, but it does not protect the active drafting path.

### F1-03 — Convention evidence is collected only in tests

**Severity:** Medium
**Class:** Capability built but unreachable
**Remediation:** Closed 2026-08-28 in Phase 9 by deletion. No product decision
required the dormant evidence abstraction, so its module, exports, and test-only
consumer were removed rather than inventing a surface.

`collectConventionEvidence` and `evidenceStanding` can combine rejected patches, contracts, diffs, write intent, and human guidance into durable convention evidence. No production consumer invokes either function, so the product cannot benefit from the mechanism.

### F1-04 — Provider quota parsing has no production caller

**Severity:** High
**Class:** Capability built but unreachable
**Remediation:** Closed 2026-08-28 in Phase 9. Every adapter result now passes
through the existing parser and appends a typed `provider.quota_observed`
transition when real provider windows exist; failure to preserve that evidence
fails visibly after process settlement.

`parseProviderQuota` understands provider rate-limit data and is covered by tests, but it has no production caller. The UI therefore cannot display the provider quota information this parser was designed to supply.

### F1-05 — An internal token ceiling is presented as provider-reported quota

**Severity:** High
**Class:** Contract and copy mismatch
**Remediation:** Closed 2026-08-28 in Phase 9. Internal Hivemind spending limits
and provider-reported reset windows have separate sources, projections, and
copy; only the latter renders provider plan/remaining percentages.

The only production `quota.exhausted` producer found reports `source: "token_ceiling"`, which is Hivemind's configured limit. The Project surface labels the projected value as something the provider reported. This turns an internal safety ceiling into a false statement about the external provider.

### F1-06 — Provider setup has no durable event trail

**Severity:** High
**Class:** Audited state gap
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Provider
setup now records a durable start and exactly one typed completion or failure,
with open-round reconciliation covering interrupted setup.

Provider configuration and adapter probing change setup-visible state, but the event contract has no provider-setup or adapter-setup event family and the active configuration/probe paths append no equivalent durable event. A consequential setup transition therefore lacks the event evidence used elsewhere as Hivemind's source of truth.

### F1-07 — Conversation activity can freeze silently

**Severity:** High
**Class:** Runtime failure hidden from the surface

The conversation activity stream installs an `onerror` handler that does nothing. If that stream disconnects while work continues or stalls, the visible liveness feed can freeze without an error, retry state, or terminal explanation.

### F1-08 — Stream messages are trusted after only JSON parsing

**Severity:** High
**Class:** Boundary validation gap

The shared stream parser performs `JSON.parse` and casts the result to the requested TypeScript type. Valid JSON with the wrong shape is accepted; invalid JSON becomes `null` and is silently discarded. Event and output stream contracts are therefore not validated at the client boundary.

### F1-09 — The `context.low` UI state has no producer

**Severity:** High
**Class:** Surface built but unreachable
**Remediation:** Closed 2026-08-28 in Phase 9 by deleting the unproduced event
name and every dead projection/thread branch. No replacement warning was
invented without a real Core transition.

Desktop projection and Work-screen copy handle `context.low`, but no production Core path emits that event. The warning exists in the interface and cannot occur in real use.

### F1-10 — Build-mismatch recovery can retain a stale project path

**Severity:** Medium
**Class:** Stale closure
**Remediation:** Closed 2026-08-28 in Phase 9. The workspace session now depends
on the current recovery callback and exposes the exact failed last-project read
with a retry bound to the current selection.

Build-mismatch recovery depends on the selected project path, but the memoized workspace session omits the recovery callback from its dependency set. After a project change, a mismatch can therefore recover against an older path.

### F1-11 — Autonomy-setting failures are discarded

**Severity:** Medium
**Class:** Failure collapsed into apparent success
**Remediation:** Closed 2026-08-28 in Phase 9. Settings awaits the audited write,
keeps the selected durable value authoritative, and renders a shared retryable
failure when the write refuses.

The Settings autonomy control fires the action without awaiting or handling rejection. A failed write has no local error state and can leave the user believing the selection was saved.

### F1-12 — Account inspection failure removes the account surface

**Severity:** Medium
**Class:** Failure collapsed into absence
**Remediation:** Closed 2026-08-28 in Phase 9. Accounts remains mounted on fresh
and active Project surfaces, names inspection failure, and offers an exact
retry; its Add control reaches `accounts.add` through both OS folder selection
and manual path entry.

The accounts panel converts an `accounts.inspect` failure into `null`. The resulting blank/absent surface is indistinguishable from there being nothing to show and provides no recovery action.

### F1-13 — Configuration inspection failure removes spend information

**Severity:** Medium
**Class:** Failure collapsed into absence
**Remediation:** Closed 2026-08-28 in Phase 9. Configuration failure is a named
retryable state. Provider usage is projected only from its own durable provider
event, so an unrelated config read can neither erase it nor fabricate it.

The Project surface suppresses the configuration panel when `config.inspect` fails. Its downstream spend panel also returns nothing when provider data is absent, so session spend can disappear because an unrelated configuration read failed.

### F1-14 — Provenance inspection failure suppresses its qualifier

**Severity:** Medium
**Class:** Failure collapsed into a stronger claim
**Remediation:** Closed 2026-08-28 in Phase 9. Unknown provenance remains an
explicit retryable qualifier and never falls through to the stronger
no-evidence-missing presentation.

The provenance note maps a failed checks inspection to `missing = false`. Instead of saying provenance could not be established, the surface removes the qualifier and can present a more confident state than the evidence supports.

### F1-15 — Recent-project registry failures are silent

**Severity:** Medium
**Class:** Persistence failure hidden from the user
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Load,
remember, and remove failures remain explicit and retryable; missing entries
stay visible with a reachable remove action.

Loading, remembering, and forgetting recent projects all discard failures. This is one boundary defect with three symptoms: the switcher can omit projects, a chosen project can fail to persist, and a removed project can return after restart without any explanation.

## Phase 2 confirmed findings

### F2-01 — Setup preselects a provider the user cannot deselect

**Severity:** High
**Class:** Paid-action selection defect
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Setup
starts with no provider selected, keeps every eligible selection reversible
until activation, and derives its estimate from the exact selected connection
plan.

Setup derives its initial selection from product-wide support status rather than this machine's authentication standing. On the installed screen Grok was checked, its checkbox was disabled, the row said `Sign in` / `Not signed in`, and Continue remained enabled. The disclosed plan was about 160,000 tokens. A user therefore cannot remove a selected provider before the paid check that the selection controls.

### F2-02 — The primary Kimi setup path can never complete its own prerequisite

**Severity:** High
**Class:** Surface deadlock
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Installed
providers whose authentication status cannot be read are presented as
unverifiable and can be explicitly selected for the bounded connection proof;
they are never relabelled signed in.

Setup enables a provider checkbox only after the authentication inspector returns `signed_in` (or after the provider was already checked in this project). Grok and Kimi deliberately have no safe status command, so both remain `unknown` after their sign-in handoff. Kimi is not preselected, leaving its checkbox permanently disabled on the primary onboarding surface. Settings can connect a separately configured Kimi model, but the setup flow itself neither reaches that path nor explains the workaround.

### F2-03 — Unknown authentication is stated as “Not signed in”

**Severity:** Medium
**Class:** Evidence overstated
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Signed
out, unknown, unverifiable, missing, malformed, and failed are distinct typed
states with evidence-matched copy.

The shared provider standing maps every connectable state other than `signed_in` to `Not signed in`. That includes an unavailable status command, a timed-out status check, and unrecognised output. The installed Grok and Kimi rows therefore stated a negative fact Core explicitly reported as unknown.

### F2-04 — Missing provider CLIs are reported as installed on Windows

**Severity:** High
**Class:** Platform-specific detection defect
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Core checks
the intended provider executable through PATH/PATHEXT before either status or
sign-in launch; a restricted-PATH installed-Core probe reported all five
providers missing rather than mistaking `cmd.exe` for the child.

The Windows read-only invocation starts `cmd.exe` and asks it to run the provider's `.cmd` file. Missing-executable detection checks whether the outer process failed with `ENOENT`; `cmd.exe` exists, so a missing Codex, Claude, or OpenCode child is reported as `installed: true`. A direct installed-Core probe with `PATH` restricted to `System32` reproduced all three false installed results. The same nesting lets the sign-in launcher report success when it merely opened a terminal whose inner provider command can fail, making OpenCode's recorded install guidance unreachable when it is most needed.

### F2-05 — Provider-authentication inspection failures are unhandled

**Severity:** Medium
**Class:** Failure hidden from the surface
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. The shared
authentication hook retains a scoped error and retry action instead of leaving
an unhandled promise or stale standing.

The provider-authentication hook calls its initial and interaction-triggered refreshes with `void refresh()` and no rejection handler. If `provider.auth.inspect` rejects, the promise is unhandled, no row-local error appears, and the empty/previous standing remains on screen. This is a provider-specific instance not covered by Phase 1's configuration, account, or recent-project failure findings.

### F2-06 — Opening a project automatically executes repository code

**Severity:** High
**Class:** Unsafe product policy
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Detection
only recommends the command; `checks.try` exists solely behind the answering
Run control. The installed marker stayed absent before that click.

After setup detects a check command, the Checks step dispatches `checks.try` from an effect without a Run click or confirmation. The installed probe created a Git project whose `npm test` only wrote a marker; clicking `Set up this folder` created `auto-check-ran.txt` before any check control was pressed. A real package script may use the network, modify data, start services, or perform other side effects. Detecting a command is not authorization to execute it.

### F2-07 — One-click Git's shallow scan can commit secrets and generated trees

**Severity:** High
**Class:** Destructive boundary gap
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. A confined
recursive inventory honors root ignore rules, refuses secret-name variants,
nested repositories, and links, excludes nested generated trees, and stages
only the exact reviewed set.

The secret refusal recognizes six exact top-level names, so the installed app offered `Set up git for me` for a fixture containing `.env.production`. Generated-directory handling is also top-level only: a monorepo fixture's `packages/app/node_modules/dep.js` and `packages/app/dist/bundle.js` were both included in the first commit. The UI says generated or ignored files will not enter the first commit, but common nested dependency/build layouts violate that claim.

### F2-08 — A valid nested-source project is classified as having no source

**Severity:** Medium
**Class:** False setup refusal
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Recursive
classification finds nested source; the installed fixture reached the setup
preview through `src/index.js` while nested dependencies remained excluded.

The folder classifier skips every directory and recognizes source only from top-level files. The installed app refused a fixture whose real source was `src/index.js`, stating that the folder had no source files and offering only another folder. This common greenfield layout is unusable until the user adds an unrelated recognized top-level file or initializes Git manually.

### F2-09 — A failed manual path is cleared as though it opened

**Severity:** Medium
**Class:** Failed action presented as completion
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Manual
selection closes only after a usable project result; a failed path remains
visible and editable in the same dialog.

The project session returns `{ ok: false }` rather than throwing on an open failure, but the dialog submit handler ignores the result, clears the text field, and closes the dialog unconditionally. The installed probe typed a nonexistent path and confirmed the dialog closed while the setup screen showed the failure. Correcting one character requires reopening the dialog and retyping the whole path.

### F2-10 — Installed E2E walks pollute the user's real project history

**Severity:** Medium
**Class:** Test isolation failure
**Remediation:** Closed 2026-08-28. Every installed JavaScript driver is guarded
by the shared exact-byte recent-project snapshot/restore helper, and a static
test rejects any future unguarded driver.

The installed scripts open their fixtures through the real app and none except the new Phase 2 probe snapshots/restores `recent-projects.json`. Before this audit, five of the eight installed recent entries were recognisable E2E/walk fixtures. These entries affect the production project switcher and can become the folder the app tries to reopen on a later cold start. A verification tool is changing the behavior it is meant to observe.

### F2-11 — The recent-project registry is non-atomic and corrupts to empty

**Severity:** Medium
**Class:** Persistence durability gap
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Registry
writes use a same-directory temporary file, sync, and write-through replacement;
malformed or unreadable state is preserved and reported as corruption.

Remember and forget rewrite the registry with direct `std::fs::write`, unlike the project's authoritative atomic-write convention. A crash or interruption can leave partial JSON; the next read silently converts any read/parse failure to an empty list. Phase 1 F1-15 records that the client hides command failures; this finding is the distinct underlying durability and corruption behavior even when no command rejects.

### F2-12 — Cold-open copy offers a removal control that cannot exist

**Severity:** Medium
**Class:** Unreachable recovery
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Missing
recent folders remain in the cold-open/project list as disabled open targets
with a reachable remove action.

When the last project folder is missing, cold open says to choose a folder “or remove it from the list.” The project menu obtains `recent_projects`, which filters missing directories out, and there is no selected current project when this error is shown. The named removal option is therefore absent from the only surface that can perform it.

### F2-13 — Finishing Git setup can switch the user back to an old project

**Severity:** High
**Class:** Cross-project race
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Project
open and Git initialization share generation identity; a stale completion
cannot reopen or replace a newer selection.

The project switcher remains enabled while one-click Git runs. `initializeGit` captures the old path and, after the shell action finishes, unconditionally starts a new `session.switchProject(oldPath)`. If the user opens another project during the Git operation, this later switch advances the session generation and reselects the old project. The generation guard protects ordinary overlapping opens, but this follow-up creates a fresh winning generation after the user's newer choice.

### F2-14 — Corrupt provider artifacts are reported as never installed

**Severity:** Medium
**Class:** Corruption collapsed into absence
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Provider
profiles, connections, and accounts are shape-validated; malformed artifacts
remain visible as corruption rather than becoming clean absence.

Profile JSON parse/read failure produces an adapter row with `installed: false` and an empty `problems` list; malformed connection JSON becomes `null`; malformed `accounts.json` becomes an empty account file. The installed-Core probe wrote malformed planner profile and connection files and received a clean “not installed” planner record. Setup cannot distinguish “you never configured this” from “configuration on disk is damaged.”

### F2-15 — An incomplete `.git` marker enters a false-success loop

**Severity:** Medium
**Class:** Lifecycle state misclassified
**Remediation:** Closed 2026-08-28 in installed build **26.828.510**. Readiness
asks Git to prove the repository; an incomplete marker is refused and no setup
action is offered.

Git readiness treats any existing `.git` path as an existing repository without asking Git whether it is valid. Project opening correctly fails `git rev-parse`, the setup screen still offers Git setup, and `initialize_git` immediately returns success because the marker exists. The subsequent reopen fails the same check. An interrupted/manual `git init` can therefore produce a recovery button that reports success while making no repair.

## Phase 2 shared causes

The 15 Phase 2 findings cluster around five recurring design mistakes:

1. **One state used for different facts:** product support, local sign-in, project capability, and executable presence are conflated in F2-01 through F2-04.
2. **A detected mechanism treated as consent:** F2-06 executes a repository script merely because it was found; F2-07 commits files merely because a shallow scan did not name them.
3. **Shallow classification at a destructive boundary:** F2-07, F2-08, and F2-15 decide repository safety or validity from top-level names/markers rather than the tree or Git's own answer.
4. **Failures collapsed into a successful/empty presentation:** F2-05, F2-09, F2-11, and F2-14.
5. **Lifecycle work is not isolated by project and actor:** F2-10 and F2-13 let verification activity or an old operation change what the user opens next.

Phase 2 raises the cumulative open count to **36 distinct findings**. The installed probe also reproduced F1-21 (`git status --porcelain` returned `?? .hivemind/` after the two one-click steps); it is evidence for the existing finding and was not counted again.

## Phase 3 confirmed findings

### F3-01 — Conversation events and read-only inspection wait for the whole provider call

**Severity:** High
**Class:** Real-time architecture defeated by serialization

The daemon puts every non-interrupt workspace action, including `status.inspect`, through one serialized queue. It snapshots the event count before the action and publishes newly durable events only after the handler returns. During an installed four-second answer, `conversation.message_recorded` was already on disk, but the request was absent from the thread and absent from the live event stream; a separately issued read-only status inspection remained blocked for 3,209 ms. The live message arrived 4,285 ms after send, alongside the finished answer. The activity output channel has its own publisher, which is why `Thinking` could appear while the person's already-recorded request could not. This is one queue/publication boundary defect, not three separate missing-screen bugs.

### F3-02 — An existing spec makes the client bypass the conversation classifier

**Severity:** High
**Class:** Client-owned gate logic

`preparePlan` invokes `spec.draft` only when `inspection.active_spec_id` is absent. Once a spec exists and no plan is waiting, `submitPrompt` sends every message directly to `plan.prepare`; with work remaining it can send the message to `manager.start` instead. The installed probe left `S-001` active after a deterministic plan failure, then typed `What does this project do now?`. The sole adapter call was a planning call, no `conversation.message_recorded` event was written, and the question never appeared in the thread. A normal question can therefore be interpreted as planning or work continuation from client lifecycle state without reaching Core's typed `reply`/`spec` decision; under policy ratification the planning branch can continue into manager execution.

### F3-03 — A failed send destroys the person's text and attachments

**Severity:** High
**Class:** Failed action presented as consumption

The submit handler clears the composer and attachment array before awaiting any Core action. Its failure path shows feedback but never restores either value. In the installed active-spec reproduction, the question was routed to the failing planning call, the box was emptied, no conversation event was written, and the text was absent from the thread. Any planner, daemon, or transport failure therefore makes the person retype the request and reconstruct every attachment.

### F3-04 — One rapid submit can become two provider calls

**Severity:** High
**Class:** Paid-action reentrancy

The form has no synchronous in-flight guard. `busy` is React render state, so two submissions in the same browser turn both enter the handler with the same closed-over composer value before the disabled button renders. The installed probe issued two form submissions in one turn and observed two identical drafting prompts, two adapter processes, two durable request events, and two replies. A double click or Enter/click race can therefore spend twice and duplicate the conversation despite the visible one-message affordance.

### F3-05 — Conversation context describes the committed base, not the current project

**Severity:** High
**Class:** Stale project evidence

Conversation context starts from `trackedFilesAtBase`, which runs `git ls-tree` against the current base commit. It then reads current contents only for those committed names. New and untracked files — and the new side of a rename — are absent even though they are often the exact work a person is asking about. The fixture's tracked README and `src/index.ts` contents reached the captured model prompt, while the name and unique contents of `UNTRACKED-CURRENT.md` did not. The answer can be internally grounded and still be wrong about the project currently on disk.

### F3-06 — Attaching a folder sends its label, not its contents

**Severity:** Medium
**Class:** Affordance without a matching Core capability

The folder picker creates an attachment chip, but submission converts every attachment to an `@path` line in ordinary prompt text. Context scoring promotes an exact file path or basename; it does not expand a folder or reserve a bounded subtree slice. The installed fixture submitted the exact generated shape `Project references: - @notes`. The captured prompt listed the tracked child `notes/current-behavior.yaml` in the global filename appendix but omitted its unique content. The visible “Folder…” attachment therefore does not supply the folder evidence it appears to attach.

### F3-07 — “New conversation” is not a clean conversation boundary

**Severity:** High
**Class:** Product semantics contradict durable state

Core's `conversation.new` deliberately appends only `conversation.started`; it preserves the active spec and any prepared plan. The client says “the board is clear” and its confirmation copy says a waiting plan will be cleared. In the installed probe, starting a new conversation hid the earlier thread but left active spec `S-001`. The first question in the blank conversation again went directly to `plan.prepare`, was not recorded, and vanished. The control changes presentation history while leaving the lifecycle state that controls what new messages mean.

### F3-08 — Most orchestrator calls have no live-output path

**Severity:** High
**Class:** Functional progress designed out

`runAdapterProcess` exposes `onStreamChunk`, but production uses it for the initial spec draft and worker execution only; the quality provider collects chunks privately. Planning, manager proposals, redirect correction, Scout, ideation, and memory consolidation invoke the same process runner without a publisher. During the installed `plan.prepare` call, the fake adapter emitted a valid activity record but the screen could only retain a generic wait; no adapter activity reached it. Long orchestration stages can therefore remain silent even though the process already exposes stream chunks.

### F3-09 — Live activity understands Codex and silently ignores the other supported providers

**Severity:** High
**Class:** Provider-specific implementation behind a provider-neutral surface

`activityLine` recognizes Codex event names and item shapes only. The product supports Claude Code, OpenCode, Grok Build, and Kimi Code, and has separate usage parsers for their output, but their stream records have no activity decoder. A direct installed-Core probe produced `Thinking` for a Codex record and no activity for a representative Claude `assistant` stream record. Those providers may complete successfully while their functional liveness surface stays blank.

### F3-10 — Valid JSONL activity is lost when the operating system splits a record

**Severity:** Medium
**Class:** Stream framing defect

The adapter passes each raw Node `data` chunk to the output writer. `activityLines` splits and parses each chunk independently and keeps no carry buffer. The installed decoder returned `Thinking` for one complete Codex JSONL record and returned no lines when the identical bytes were split across two chunks. Chunk boundaries are not record boundaries, so liveness can disappear nondeterministically with provider output size and operating-system buffering.

### F3-11 — Plain-text progress is unconditionally discarded

**Severity:** Medium
**Class:** Explicit no-op branch

The activity decoder's comment says readable non-JSON stderr sentences are retained, but the implementation returns `null` from both sides of its condition. The installed-Core probe passed `Inspecting project files` and received no activity. Any harness that reports progress as plain text — including fallback chatter from an otherwise supported harness — is guaranteed to look silent.

### F3-12 — Draft activity write failures are converted into success

**Severity:** Medium
**Class:** Failure suppressed at the liveness boundary

The spec-draft stream chains `appendTaskOutput(...).catch(() => undefined)` and awaits the resulting tail. A failed append, corrupt output trail, or publication-path write error is therefore discarded while drafting continues and can return a successful reply. Worker output uses the same writer without this suppression. The conversation surface can lose its functional progress record and receive no warning, recreating the exact “mechanism exists on disk but the screen is silent” shape this channel was meant to prevent.

## Phase 4 confirmed findings

### F4-01 — Stop records cancellation while manager judgment keeps running and executes afterward

**Severity:** Critical
**Class:** Cancellation event without cancellation enforcement

`cancelManagerRun` appends `scheduler.run_cancel_requested`, stops plan tasks, and appends `scheduler.run_cancelled`, but the reactive manager loop checks that record only in concurrent-wave launch helpers. It neither terminates an in-flight manager provider process nor checks cancellation before generating and executing the next ordinary action. The isolated probe stopped a session while its manager process was sleeping: Stop returned in 30 ms, the process was still alive, and its later `get_status` proposal was consumed and executed. A control that says work stopped can therefore be followed by additional judgment, paid usage, and state-changing actions.

### F4-02 — A cancelled manager session is reconstructed as active and continuable

**Severity:** Critical
**Class:** Durable truth omitted from projection

Manager-session history derives status from pending, blocked, and proposed-action fields only; it does not read `scheduler.run_cancel_requested` or `scheduler.run_cancelled`. The cancelled fixture session was returned as `status: active` with `continuation_available: true`. Installed build 26.826.1622 then rendered `Waiting on the next agent`, `WORK IS RUNNING`, a running clock, and another Stop button, with no cancellation text. This is not a stale frame: it is the deterministic reconstruction after cancellation.

### F4-03 — The first manager proposal has no discoverable stop or restart boundary

**Severity:** High
**Class:** In-flight work exists before its controllable identity

`startManagerSessionWithId` calls the manager before writing the manager-session artifact or recording the run start. While the fixture manager process was alive, the session directory was unchanged. Context-pressure events were durable, but both carried null task/session/run identifiers; the internally generated ID was not exposed through the client and `run.stop` could not load a session for it. If the first proposal hangs or the app restarts, the person has no run to stop and recovery cannot distinguish an intentional absence from an abandoned manager call.

### F4-04 — Starting a new conversation can write a false cancellation onto completed history

**Severity:** High
**Class:** Terminal state ignored at a lifecycle boundary

The Work surface computes `runActive` by excluding complete/stopped sessions, but `startNewConversation` calls `run.stop` whenever any `managerSession` exists. Core's stop action has no guard for a completed manager session, so it appends cancellation-requested and cancellation-terminal events even when there is nothing active to cancel. Merely opening a clean thread after completed work can rewrite the durable interpretation of that finished run and poison later history/recovery projections.

### F4-05 — One successful answer path ignores failure to close its durable draft round

**Severity:** High
**Class:** Partial durable write reported as success

The answer-only branch of `spec.draft` correctly checks the `conversation.reply_recorded` append, then awaits `spec.draft_failed` without checking its result and returns success. If that second append fails, the answer appears successful but the prior `spec.draft_started` remains open forever. This is distinct from F3-12's discarded activity-output write: here the authoritative lifecycle pair itself is incomplete, so restart can faithfully reconstruct drafting that is no longer happening.

### F4-06 — Recovery collapses distinct quality drafts and scheduler waves into one round

**Severity:** High
**Class:** Non-unique durable round identity

`openRounds` keys `quality.draft_started` only by task ID and `scheduler.wave_started` by an empty task ID because both shapes declare no identity field. Two quality drafts for one task therefore replace each other; all taskless scheduler waves replace each other. The scoped probe supplied two of each and recovered one quality round and one wave. A crash with multiple in-flight rounds can hide all but the last, so cleanup and the UI reason about less work than actually started.

### F4-07 — A retryable quality cancellation failure is treated as a closed round

**Severity:** High
**Class:** Failed cleanup classified as terminal cleanup

The open-round vocabulary lists `quality.cancel_failed` as terminal unconditionally. The event itself can say `retryable: true` and `cleanup_complete: false`, but that still deletes the round. The probe opened a quality draft and appended exactly that retryable failure; recovery returned no open round. The remaining process/resource cleanup is hidden at the moment the event says it still needs another attempt.

### F4-08 — Abandoned rounds without an ID are deliberately filtered out of the client

**Severity:** High
**Class:** Recovery mechanism unreachable from its surface

Core's round reconciler detected an old `scheduler.wave_started` record as abandoned with `id: null`. `inspectWorkspace` converts reconciled rounds to their IDs and filters nulls before publishing `silent_rounds`, so the installed client received an empty list. Integration, adoption, scheduler, and other taskless rounds can therefore be correctly identified as abandoned inside Core and still never reach the screen that must tell the person recovery is needed.

### F4-09 — A crash between quota reservation and process binding permanently holds the reservation

**Severity:** Critical
**Class:** Crash window with no reclaimable owner

Metered-call reservation writes `process_identity: null` before spawning and binding the provider process. Reconciliation retains every active reservation whose identity is null, regardless of daemon liveness or age. The probe created that exact post-reservation/pre-bind crash state; restart reconciliation reported it retained and continued holding 150,000 reserved tokens. Repeated crashes in this narrow window can exhaust a session ceiling without any provider call running or any usage evidence available to settle.

### F4-10 — A crash between `task.resumed` and `task.started` leaves a task running forever

**Severity:** Critical
**Class:** Non-atomic resume transition outside startup reconciliation

Resume appends `task.resumed` before the new run is accepted and started. Workspace projection treats that event as running, while startup reconciliation only examines tasks with an unmatched `task.started` or open cancellation. The probe appended a paused/resumed boundary and simulated restart: reconciliation examined no tasks and inspection still reported the task as running. A crash in this real ordering produces a permanent live task with no process for Stop or startup cleanup to find.

### F4-11 — A late background failure regresses a cancelled task to failed

**Severity:** High
**Class:** Terminal-state regression

`markRunFailed` protects completed and already-failed tasks but not cancelled tasks. Because task state is derived from the latest terminal event, any late rejection from detached `finishPreparedRun` can append `task.failed` after `task.cancelled`. The probe started and cancelled a task, called the production failure marker, and observed state change from `cancelled` to `failed`. The human's successful Stop is overwritten by an implementation race, and retry/cleanup behavior then follows the wrong terminal meaning.

### F4-12 — Partial run-stop failure is durable but never becomes “Needs you”

**Severity:** Critical
**Class:** Actionable recovery fact has no consumer

`cancelManagerRun` durably emits `scheduler.run_cancel_failed` with the tasks stopped, failures, and `retryable: true` when any task cannot be cleaned up. Workspace inspection has no consumer for that event. The probe appended a partial-stop failure and confirmed it was on disk while no matching `needs_you` item was published. Stop can therefore fail with a worker or lease still alive, then disappear from the persistent UI after the transient action error is gone. This standing design-note gap is now reproduced and counted; it was not counted in Phases 1–3.

### F6-01 — The daemon is an unauthenticated command-and-data control plane

**Severity:** Critical

**Class:** Trust boundary absent

`createDaemonServer` applies no token, authorization, Host, Origin, or content-type check to any route. Its GET routes expose health, events, and task output; its POST routes include every mutable workspace action and the actions Core treats as coming from a human surface. The installed-Core probe sent `checks.try` with no authorization header, `Origin: https://untrusted.example`, and `Content-Type: text/plain`; the daemon returned 200, executed the supplied shell command, and created `phase6-unauthenticated-action.txt`. daemons refuse non-loopback binding and independently enforce loopback Host,
the reviewed Tauri development/production Origins, and JSON POST content type.
Version-1 daemon records are never queried: an idle project uses the existing
restart recovery to replace the legacy process, while active or ambiguous work
keeps the restart guard closed.

credential-free request against installed build **26.827.2222** returned 401 and
did not write the marker; a wrong credential returned 401, a correct credential

Medium, 2 Low)**.

### F6-11 — The release command can publish a stale installer under an unrelated commit

**Severity:** Critical

**Class:** Artifact provenance unbound

**Remediation:** Closed 2026-08-29 by Phase 14. The approved manual workflow
builds and installs one clean artifact, then the publisher rechecks exact HEAD,
an empty tracked/untracked diff, the configured origin, the public branch head,
the immutable manifest source commit, and the matching installation receipt
before it can create a draft. The draft receives the already-admitted bytes;
their complete descriptor is verified while private. Upload, verification,
publish-response, public-state, or `/releases/latest` mismatch deletes the
private draft or withdraws an observed public release. The transaction's
upload, verification, ambiguity, rollback, tag-reuse, and source mismatch
branches passed the offline rehearsal. No public release was used as rehearsal.

`release:github` does not build, install, test, audit, or require a clean tree. `release-local.mjs` signs whichever existing installer matches ignored `gen/app-version.txt`; `publish-github-release.mjs` independently reads current `HEAD` and creates the release tag against it. A stale or locally modified installer can therefore be signed and published as a release whose Git tag points at different source.

### F6-12 — Release verification is weaker than the updater and occurs after publication

compares the descriptor and both immutable manifests, compares installer and

`verify-release.mjs` accepts any signature-looking string longer than 100 characters and an installer whose HEAD response exceeds 1 MB. Both the installed executable and current installer return `NotSigned` from `Get-AuthenticodeSignature`. This is already documented as an intentional beta choice, not a newly discovered implementation oversight, but it is counted here because this audit explicitly includes large designed-in production issues. Ed25519 protects only the in-app updater path; the first downloaded installer has no Windows publisher identity, cannot establish SmartScreen reputation, and asks nontechnical users to bypass an operating-system warning for a product whose own promise is verified execution.

### F6-18 — Calendar versions collide for every build in the same minute

**Severity:** High

**Class:** Release identity is not unique

**Remediation:** Closed 2026-08-29 by Phase 12. Versions encode epoch
milliseconds into three Windows-safe fields and advance from persisted state
when the same millisecond repeats or the clock moves backward. The artifact ID
also hashes the complete admitted artifact manifest.

`stamp-version.mjs` encodes only year, month/day, hour, and minute. Two builds in one minute produce the same version, installer filename, release tag, uninstall version, and updater comparison value. A second local build can overwrite the first artifact while both claim one identity; a second publication cannot reuse the tag; and the next-launch marker can report success immediately because the old running binary already equals the attempted version. Clock rollback adds a non-monotonic variant. Existing tests cover formatting and sampled order, not uniqueness under an actual repeated minute.

### F6-19 — Source-update staleness watches the wrong set of build inputs

**Severity:** Medium

**Class:** Freshness classifier has false positives and false negatives

**Remediation:** Closed 2026-08-29 by deletion. Phase 10 removed source-update
discovery and freshness classification; Phase 11 did not recreate either.
R2 owns one manifest-bound immutable artifact identity instead.

The classifier takes the newest timestamp under four source directories and the timestamp of the repository's latest commit. Any documentation/evidence-only commit can therefore offer a rebuild even though no build input changed. In the other direction, uncommitted changes to `package.json`, lockfiles, `Cargo.toml`, Tauri configuration, capabilities, icons, Vite/TypeScript configuration, installer hooks, and other real build inputs are outside `SOURCE_DIRS` and can remain invisible. A timestamp heuristic cannot answer artifact provenance, and this one does not even enumerate the build graph it approximates.

### F6-20 — Non-Windows package scripts bypass versioning and the source updater cannot install their output

**Severity:** Medium

**Class:** Cross-platform commands do not form a release path

**Remediation:** Closed 2026-08-29 by quarantine. The unsupported Linux and
macOS script names are removed, Tauri targets NSIS explicitly, and the current
qualified packaging/install contract declares Windows x64 only.

`tauri:build:linux` and `tauri:build:mac` call bare `tauri build`, bypassing `bundle:stamp` and its generated version overlay, while checked-in configuration remains `0.0.0`. The in-app source-update path always searches for a Windows NSIS filename and `spawn_swap` is Windows-only, even though `bundle.targets` says `all` and the updater plugin supports desktop platforms. The repository therefore contains named Linux/macOS build commands that cannot produce the same versioned, self-installing artifact contract as Windows.
