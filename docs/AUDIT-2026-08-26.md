# Full-codebase audit — 2026-08-26

This is the durable ledger for the seven-phase audit requested on 2026-08-26. It is intentionally evidence-first: a finding is recorded only when the active production path and the failing or missing boundary were inspected. ## Confirmed findings

### F1-01 — Eight audited actions have no product surface

**Severity:** High
**Class:** Capability built but unreachable

`accounts.add`, `manual_task.authorize`, `manual_task.review`, `memory.review_handoff`, `quality.best_of_n`, `quality.cancel`, `quality.draft_refine`, and `verify.characterize` are registered and audited Core actions, but neither the desktop client nor a Core-published queued action invokes them. The mechanism exists; the product cannot reach it.

### F1-02 — The non-goal quality gate is test-only

**Severity:** High
**Class:** Guarantee built but not enforced

`assessNonGoals` detects vacuous entries such as `"None"`, but no production path calls it. A direct probe showed the drafted-answer parser accepts a valid-looking specification containing `non_goals: ["None"]` while `assessNonGoals(["None"])` correctly rejects the same content. The check is real and tested, but it does not protect the active drafting path.

### F1-03 — Convention evidence is collected only in tests

**Severity:** Medium
**Class:** Capability built but unreachable

`collectConventionEvidence` and `evidenceStanding` can combine rejected patches, contracts, diffs, write intent, and human guidance into durable convention evidence. No production consumer invokes either function, so the product cannot benefit from the mechanism.

### F1-04 — Provider quota parsing has no production caller

**Severity:** High
**Class:** Capability built but unreachable

`parseProviderQuota` understands provider rate-limit data and is covered by tests, but it has no production caller. The UI therefore cannot display the provider quota information this parser was designed to supply.

### F1-05 — An internal token ceiling is presented as provider-reported quota

**Severity:** High
**Class:** Contract and copy mismatch

The only production `quota.exhausted` producer found reports `source: "token_ceiling"`, which is Hivemind's configured limit. The Project surface labels the projected value as something the provider reported. This turns an internal safety ceiling into a false statement about the external provider.

### F1-06 — Provider setup has no durable event trail

**Severity:** High
**Class:** Audited state gap

Provider configuration and adapter probing change setup-visible state, but the event contract has no provider-setup or adapter-setup event family and the active configuration/probe paths append no equivalent durable event. A consequential setup transition therefore lacks the event evidence used elsewhere as Hivemind's source of truth.

### F1-07 — Conversation activity can freeze silently

**Severity:** High
**Class:** Runtime failure hidden from the surface

The conversation activity stream installs an `onerror` handler that does nothing. If that stream disconnects while work continues or stalls, the visible liveness feed can freeze without an error, retry state, or terminal explanation.

### F1-08 — Stream messages are trusted after only JSON parsing

**Severity:** High
**Class:** Boundary validation gap

The shared stream parser performs `JSON.parse` and casts the result to the requested TypeScript type. Valid JSON with the wrong shape is accepted; invalid JSON becomes `null` and is silently discarded. Event and output stream contracts are therefore not validated at the client boundary.

### F1-09 — The `context.low` UI state has no producer

**Severity:** High
**Class:** Surface built but unreachable

Desktop projection and Work-screen copy handle `context.low`, but no production Core path emits that event. The warning exists in the interface and cannot occur in real use.

### F1-10 — Build-mismatch recovery can retain a stale project path

**Severity:** Medium
**Class:** Stale closure

Build-mismatch recovery depends on the selected project path, but the memoized workspace session omits the recovery callback from its dependency set. After a project change, a mismatch can therefore recover against an older path.

### F1-11 — Autonomy-setting failures are discarded

**Severity:** Medium
**Class:** Failure collapsed into apparent success

The Settings autonomy control fires the action without awaiting or handling rejection. A failed write has no local error state and can leave the user believing the selection was saved.

### F1-12 — Account inspection failure removes the account surface

**Severity:** Medium
**Class:** Failure collapsed into absence

The accounts panel converts an `accounts.inspect` failure into `null`. The resulting blank/absent surface is indistinguishable from there being nothing to show and provides no recovery action.

### F1-13 — Configuration inspection failure removes spend information

**Severity:** Medium
**Class:** Failure collapsed into absence

The Project surface suppresses the configuration panel when `config.inspect` fails. Its downstream spend panel also returns nothing when provider data is absent, so session spend can disappear because an unrelated configuration read failed.

### F1-14 — Provenance inspection failure suppresses its qualifier

**Severity:** Medium
**Class:** Failure collapsed into a stronger claim

The provenance note maps a failed checks inspection to `missing = false`. Instead of saying provenance could not be established, the surface removes the qualifier and can present a more confident state than the evidence supports.

### F1-15 — Recent-project registry failures are silent

**Severity:** Medium
**Class:** Persistence failure hidden from the user

Loading, remembering, and forgetting recent projects all discard failures. This is one boundary defect with three symptoms: the switcher can omit projects, a chosen project can fail to persist, and a removed project can return after restart without any explanation.

### F1-16 — Settings contains user-visible mojibake

**Severity:** Medium
**Class:** Presentation defect

At least five active Settings strings contain damaged encodings, including a range separator, loading ellipses, a fallback dash, and recommendation copy. These strings can render as `Ã...` sequences in the installed interface.

### F1-17 — Seven additional event names have no production producer

**Severity:** Low
**Class:** Contract drift

Besides `context.low`, the declared names `task.submitted`, `task.in_review`, `task.integrated`, `lease.requested`, `patch.revision_requested`, `approval.required`, and `spec.ratified` have no production producer. This is counted as one contract-drift finding until Phase 2 determines whether the names are obsolete aliases or missing transitions.

### F1-18 — The unreachable-code audit reports false positives

**Severity:** Medium
**Class:** Verification defect

`npm run audit:unreached` reported functions that are passed as values rather than called with `name(` syntax, and it cannot see functions invoked dynamically from package scripts. The tool is useful for leads but its current output cannot be treated as a reachability assertion.

### F1-19 — Normal builds omit production dead-code checks

**Severity:** Low
**Class:** Maintainability control gap

The normal TypeScript configurations do not enable unused-local and unused-parameter checking. Enabling those checks as a diagnostic found 16 Core and 9 desktop production declarations or parameters currently unused. This is one missing control, not 25 separate product bugs.

### F1-20 — The current project state contradicts itself about unreachable actions

**Severity:** Medium
**Class:** Source-of-truth drift

An older section of `docs/STATE.md` says there are four unreachable actions while listing more than four identifiers/groups. Its newest section records the verified count of eight. A reader following the standing document can therefore reach two different answers.

### F1-21 — One-click Git setup commits before Hivemind writes its shared facts

**Severity:** High
**Class:** Lifecycle ordering defect

The shell's Git initializer creates the first commit before Core project initialization writes `.hivemind/config.json` and `.hivemind/.gitignore`. The promised one-click setup can finish with Hivemind's authoritative shared facts untracked and without a blocking prompt to commit them.

## Shared causes

The 21 findings are not 21 unrelated accidents. Four recurring causes dominate:

1. **Mechanism without a consumer or producer:** F1-01 through F1-04 and F1-09.
2. **Failure collapsed into absence or apparent success:** F1-07, F1-08, and F1-11 through F1-15.
3. **Duplicated, weakly typed, or drifting contracts:** F1-05, F1-10, F1-17, and F1-20.
4. **Verification that measures declarations rather than live behavior:** F1-18 and F1-19.

This is already enough evidence that the historical “built but unreachable” pattern is systemic rather than incidental.

## Phase 2 confirmed findings

### F2-01 — Setup preselects a provider the user cannot deselect

**Severity:** High
**Class:** Paid-action selection defect

Setup derives its initial selection from product-wide support status rather than this machine's authentication standing. On the installed screen Grok was checked, its checkbox was disabled, the row said `Sign in` / `Not signed in`, and Continue remained enabled. The disclosed plan was about 160,000 tokens. A user therefore cannot remove a selected provider before the paid check that the selection controls.

### F2-02 — The primary Kimi setup path can never complete its own prerequisite

**Severity:** High
**Class:** Surface deadlock

Setup enables a provider checkbox only after the authentication inspector returns `signed_in` (or after the provider was already checked in this project). Grok and Kimi deliberately have no safe status command, so both remain `unknown` after their sign-in handoff. Kimi is not preselected, leaving its checkbox permanently disabled on the primary onboarding surface. Settings can connect a separately configured Kimi model, but the setup flow itself neither reaches that path nor explains the workaround.

### F2-03 — Unknown authentication is stated as “Not signed in”

**Severity:** Medium
**Class:** Evidence overstated

The shared provider standing maps every connectable state other than `signed_in` to `Not signed in`. That includes an unavailable status command, a timed-out status check, and unrecognised output. The installed Grok and Kimi rows therefore stated a negative fact Core explicitly reported as unknown.

### F2-04 — Missing provider CLIs are reported as installed on Windows

**Severity:** High
**Class:** Platform-specific detection defect

The Windows read-only invocation starts `cmd.exe` and asks it to run the provider's `.cmd` file. Missing-executable detection checks whether the outer process failed with `ENOENT`; `cmd.exe` exists, so a missing Codex, Claude, or OpenCode child is reported as `installed: true`. A direct installed-Core probe with `PATH` restricted to `System32` reproduced all three false installed results. The same nesting lets the sign-in launcher report success when it merely opened a terminal whose inner provider command can fail, making OpenCode's recorded install guidance unreachable when it is most needed.

### F2-05 — Provider-authentication inspection failures are unhandled

**Severity:** Medium
**Class:** Failure hidden from the surface

The provider-authentication hook calls its initial and interaction-triggered refreshes with `void refresh()` and no rejection handler. If `provider.auth.inspect` rejects, the promise is unhandled, no row-local error appears, and the empty/previous standing remains on screen. This is a provider-specific instance not covered by Phase 1's configuration, account, or recent-project failure findings.

### F2-06 — Opening a project automatically executes repository code

**Severity:** High
**Class:** Unsafe product policy

After setup detects a check command, the Checks step dispatches `checks.try` from an effect without a Run click or confirmation. The installed probe created a Git project whose `npm test` only wrote a marker; clicking `Set up this folder` created `auto-check-ran.txt` before any check control was pressed. A real package script may use the network, modify data, start services, or perform other side effects. Detecting a command is not authorization to execute it.

### F2-07 — One-click Git's shallow scan can commit secrets and generated trees

**Severity:** High
**Class:** Destructive boundary gap

The secret refusal recognizes six exact top-level names, so the installed app offered `Set up git for me` for a fixture containing `.env.production`. Generated-directory handling is also top-level only: a monorepo fixture's `packages/app/node_modules/dep.js` and `packages/app/dist/bundle.js` were both included in the first commit. The UI says generated or ignored files will not enter the first commit, but common nested dependency/build layouts violate that claim.

### F2-08 — A valid nested-source project is classified as having no source

**Severity:** Medium
**Class:** False setup refusal

The folder classifier skips every directory and recognizes source only from top-level files. The installed app refused a fixture whose real source was `src/index.js`, stating that the folder had no source files and offering only another folder. This common greenfield layout is unusable until the user adds an unrelated recognized top-level file or initializes Git manually.

### F2-09 — A failed manual path is cleared as though it opened

**Severity:** Medium
**Class:** Failed action presented as completion

The project session returns `{ ok: false }` rather than throwing on an open failure, but the dialog submit handler ignores the result, clears the text field, and closes the dialog unconditionally. The installed probe typed a nonexistent path and confirmed the dialog closed while the setup screen showed the failure. Correcting one character requires reopening the dialog and retyping the whole path.

### F2-10 — Installed E2E walks pollute the user's real project history

**Severity:** Medium
**Class:** Test isolation failure

The installed scripts open their fixtures through the real app and none except the new Phase 2 probe snapshots/restores `recent-projects.json`. Before this audit, five of the eight installed recent entries were recognisable E2E/walk fixtures. These entries affect the production project switcher and can become the folder the app tries to reopen on a later cold start. A verification tool is changing the behavior it is meant to observe.

### F2-11 — The recent-project registry is non-atomic and corrupts to empty

**Severity:** Medium
**Class:** Persistence durability gap

Remember and forget rewrite the registry with direct `std::fs::write`, unlike the project's authoritative atomic-write convention. A crash or interruption can leave partial JSON; the next read silently converts any read/parse failure to an empty list. Phase 1 F1-15 records that the client hides command failures; this finding is the distinct underlying durability and corruption behavior even when no command rejects.

### F2-12 — Cold-open copy offers a removal control that cannot exist

**Severity:** Medium
**Class:** Unreachable recovery

When the last project folder is missing, cold open says to choose a folder “or remove it from the list.” The project menu obtains `recent_projects`, which filters missing directories out, and there is no selected current project when this error is shown. The named removal option is therefore absent from the only surface that can perform it.

### F2-13 — Finishing Git setup can switch the user back to an old project

**Severity:** High
**Class:** Cross-project race

The project switcher remains enabled while one-click Git runs. `initializeGit` captures the old path and, after the shell action finishes, unconditionally starts a new `session.switchProject(oldPath)`. If the user opens another project during the Git operation, this later switch advances the session generation and reselects the old project. The generation guard protects ordinary overlapping opens, but this follow-up creates a fresh winning generation after the user's newer choice.

### F2-14 — Corrupt provider artifacts are reported as never installed

**Severity:** Medium
**Class:** Corruption collapsed into absence

Profile JSON parse/read failure produces an adapter row with `installed: false` and an empty `problems` list; malformed connection JSON becomes `null`; malformed `accounts.json` becomes an empty account file. The installed-Core probe wrote malformed planner profile and connection files and received a clean “not installed” planner record. Setup cannot distinguish “you never configured this” from “configuration on disk is damaged.”

### F2-15 — An incomplete `.git` marker enters a false-success loop

**Severity:** Medium
**Class:** Lifecycle state misclassified

Git readiness treats any existing `.git` path as an existing repository without asking Git whether it is valid. Project opening correctly fails `git rev-parse`, the setup screen still offers Git setup, and `initialize_git` immediately returns success because the marker exists. The subsequent reopen fails the same check. An interrupted/manual `git init` can therefore produce a recovery button that reports success while making no repair.

## Phase 2 shared causes

The 15 Phase 2 findings cluster around five recurring design mistakes:

1. **One state used for different facts:** product support, local sign-in, project capability, and executable presence are conflated in F2-01 through F2-04.
2. **A detected mechanism treated as consent:** F2-06 executes a repository script merely because it was found; F2-07 commits files merely because a shallow scan did not name them.
3. **Shallow classification at a destructive boundary:** F2-07, F2-08, and F2-15 decide repository safety or validity from top-level names/markers rather than the tree or Git's own answer.
4. **Failures collapsed into a successful/empty presentation:** F2-05, F2-09, F2-11, and F2-14.
5. **Lifecycle work is not isolated by project and actor:** F2-10 and F2-13 let verification activity or an old operation change what the user opens next.

Phase 2 raises the cumulative open count to **36 distinct findings**. The installed probe also reproduced F1-21 (`git status --porcelain` returned `?? .hivemind/` after the two one-click steps); it is evidence for the existing finding and was not counted again.
